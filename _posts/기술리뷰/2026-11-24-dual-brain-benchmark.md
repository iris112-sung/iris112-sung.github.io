## 서론

코딩 에이전트가 한 작업에서 설계의 타당성과 구현의 정확성을 모두 검토하도록 하는 방법을 살펴보다가 Dual-Brain 저장소를 읽었다. 이 스킬은 검토를 두 역할로 나눈다. 우뇌는 설계가 문제를 해결하는지와 변경이 다른 구성 요소에 어떤 영향을 주는지 본다. 좌뇌는 실제 코드에서 입력과 출력의 계약, 경계 조건, 기존 동작을 확인한다. 메인 에이전트는 두 검토의 근거를 종합해 필요한 변경을 적용하고 최종 결과를 검증한다. 이후 작업에 필요한 결정은 프로젝트 메모리에 남길 수 있다. [Dual-Brain 한국어 README](https://github.com/sleeplesshan/dual-brain/blob/1729cfda50c18b74029ad449aa2698a6ec558c84/README.ko.md)

예를 들어 알림 발송에 Slack을 추가한다면 설계 검토에서는 기존 발송 경로를 어떻게 활용할지 살핀다. 구현 검토에서는 실제 Slack API와 기존 호출 방식, 알림을 끈 사용자의 동작을 확인한다. 여기서 두 가지 질문이 생겼다. **같은 모델과 예산에서 두 관점의 검토를 별도 에이전트에 맡기면 더 많은 과제를 해결할 수 있을까? 토큰 예산을 늘리면 완료율과 성공률은 각각 어떻게 달라질까?**

이를 확인하기 위해 같은 13개 과제에서 네 가지 에이전트 구성을 비교하고, 시간 상한을 고정한 채 토큰 상한을 1배·1.5배·2배로 바꿨다. 2배에서는 독립 검토를 맡긴 구성이 모든 과제를 끝냈고, 더 많은 산출물이 채점을 통과한 쪽은 한 에이전트가 두 관점을 모두 검토한 구성이었다. 두 결과가 갈린 이유를 살피기 위해 검토자의 발견과 최종 답변도 대조했다.

## 기존 평가 방식과 의문

원본 벤치마크의 `core5`는 알림 리팩터링, 오래된 API 제안 대응, 프로젝트 메모리 유지 등을 보는 과제 5개로 구성된다. 기본 설정은 초기 메모리 없는 단일 에이전트, 초기 메모리가 있는 단일 에이전트, Dual-Brain을 비교한다. `dry-run`에서 보이는 15건은 과제 5개와 설정 3개를 조합한 실행 계획이다. 초기 기록에는 단일 에이전트 3/5, Dual-Brain 4/5라는 결과가 있지만, 두 조건의 메모리 접근이 달랐고 이후 일부 채점 기준의 문제도 보고됐다. [원본 벤치마크 구성](https://github.com/sleeplesshan/dual-brain/blob/1729cfda50c18b74029ad449aa2698a6ec558c84/benchmarks/README.md#core-suite) · [초기 결과와 한계](https://github.com/sleeplesshan/dual-brain/blob/1729cfda50c18b74029ad449aa2698a6ec558c84/benchmarks/RESULTS.md) · [검증 기록](https://github.com/sleeplesshan/dual-brain/blob/1729cfda50c18b74029ad449aa2698a6ec558c84/benchmarks/VALIDATION.md)

여기서 두 가지 의문이 생겼다. 첫째, 메모리를 맞춰도 Dual-Brain 쪽에는 두 관점으로 검토하라는 지침이 추가된다. 점수가 오르더라도 역할 지침의 효과와 검토자를 분리한 효과가 섞여 있다. 둘째, 과제 5개에서는 성공 여부 하나가 점수를 20%p 바꾼다. 같은 과제를 다시 돌릴 때의 일관성과 새 과제를 줬을 때의 성능을 각각 확인할 필요가 있었다.

## 평가 방식 개선

### 검토 지침과 위임의 효과를 구분하기

*AI Agents That Matter*에서는 정확도를 비교할 때 호출 횟수를 늘리는 단순한 기준선도 고려하고, 정확도와 비용을 함께 보자고 제안한다. Kim 외의 연구는 모델과 도구, 계산 예산을 맞춰 조율 구조를 비교했다. PACE 프리프린트 역시 토큰과 호출 수처럼 동시에 달라지는 자원을 제시한다. 이를 바탕으로 메모리와 두 역할의 검토 기준을 공유하는 C와 D를 추가했다. [AI Agents That Matter](https://arxiv.org/abs/2407.01502) · [Towards a Science of Scaling Agent Systems](https://arxiv.org/html/2512.08296v3) · [PACE](https://arxiv.org/abs/2611.17610)

| 조건 | 실행 방식 |
| --- | --- |
| A | 기본 단일 에이전트. 초기 프로젝트 메모리 없음 |
| B | 단일 에이전트. C·D와 같은 초기 프로젝트 메모리와 사용 안내 제공 |
| C | B와 같은 메모리를 사용한다. 한 에이전트가 원본 스킬의 설계 검토와 코드 검토를 순서대로 수행한 뒤 구현 |
| D | C와 같은 메모리를 사용한다. 별도의 읽기 전용 Codex 컨텍스트 두 개가 병렬 검토하고, 세 번째 컨텍스트가 결과를 종합해 구현 |

C와 D에는 원본 스킬의 같은 역할 프롬프트와 변경 판단 기준을 줬다. C는 한 대화에서 앞선 검토 내용을 이어받고, D는 독립 검토자들의 요약을 구현 단계에 전달한다. 이 비교에는 별도 컨텍스트, 결과 전달, 병렬 실행의 효과가 함께 들어 있다. 원본 스킬은 간단한 과제에서 위임을 생략할 수 있다. 이번 실험에서는 위임 구조의 비용을 직접 관찰하기 위해 모든 과제의 C와 D에서 두 검토를 수행했다. D의 각 컨텍스트는 토큰을 개별 계측할 수 있도록 실험 실행기에서 시작했다. [Dual-Brain 원본 스킬](https://github.com/sleeplesshan/dual-brain/blob/1729cfda50c18b74029ad449aa2698a6ec558c84/SKILL.md)

### 같은 과제 반복과 새 과제 추가를 함께 하기

*On Randomness in Agentic Evals*는 SWE-bench Verified에서 6만 건을 실행했고, 선택한 반복에 따라 전체 성공률이 2.2~6.0%p 달라졌다고 보고했다. 반면 적은 문제로 전체를 추정하려면 과제 선정이 중요하다. `tinyBenchmarks`는 MMLU 약 1만 4천 문제에서 선별한 100개로 전체 점수를 추정했고, Princeton HAL은 SWE-bench Verified에서 뽑은 50개 과제를 경량 평가에 사용했다. 이 연구들을 참고해 `core5`는 고정한 채 세 번씩 실행하고, 버그 수정·리팩터링·코드 리뷰·메모리 갱신을 포함한 과제 8개를 더했다. 반복으로 같은 과제의 변동을 보고, 확장한 과제에서 비교 결과가 어떻게 달라지는지 확인하도록 설계했다. [On Randomness in Agentic Evals](https://arxiv.org/abs/2602.07150v3) · [How Many Tasks Are Enough](https://arxiv.org/abs/2607.12338) · [tinyBenchmarks](https://proceedings.mlr.press/v235/maia-polo24a.html) · [HAL SWE-bench Verified Mini](https://hal.cs.princeton.edu/swebench_verified_mini)

### 토큰 상한을 달리하고 완료와 성공을 구분하기

첫 실험에서는 공통 예산을 정해 13개 과제를 A~D에서 실행했다. C와 D는 첫 실행에서 각각 8건이 토큰 상한에 걸렸다. C와 D가 완료한 5건씩은 모두 채점을 통과했다. 이 결과가 예산이 좁아서 생겼는지 살펴보기 위해, 후속 실험에서는 **모델·과제·시간 상한·채점기는 그대로 두고 토큰 상한만 1.5배와 2배로 높였다.**

| 예산 | 단일 세션 토큰 상한 | 다중 세션 토큰 상한 |
| --- | ---: | ---: |
| 1배 | 130,000 | 320,000 |
| 1.5배 | 195,000 | 480,000 |
| 2배 | 260,000 | 640,000 |

**완료율**은 예산 안에서 요구된 실행 단계를 마친 비율이다. **성공률**은 전체 시도 중 실행을 완료하고 독립 채점을 통과한 비율이다. 그래서 예산에 걸린 시도와 실행을 끝낸 뒤 채점에 실패한 시도를 구분할 수 있다. 구현 과제는 최종 파일을 복사해 테스트했고, 읽기 전용 리뷰는 최종 판단과 결함 근거를 채점했다. 원본 과제는 기존 테스트와 소스 구조 검사도 사용했다. 메모리 파일의 문구 일치는 보조 지표로 기록했다. [최종 상태를 기준으로 한 에이전트 채점](https://www.anthropic.com/research/demystifying-evals-for-ai-agents) · [SWE-Bench Pro V2 평가 방식](https://arxiv.org/abs/2610.24206)

## 실험

### 실행 환경

모든 조건에서 `codex-cli 0.157.1`, `gpt-6-luna`, 추론 강도 `low`를 사용했다. 시간 상한은 단일 세션 120초, 다중 세션 260초로 고정했다. 매 시도는 별도 작업 사본에서 시작했고 최대 네 건을 동시에 실행했다. 캐시 입력은 전체 토큰에 포함했다. 출력 안에 포함된 추론 토큰은 한 번만 합산했다. 사용량은 모델 요청이 끝난 뒤 보고되므로, 상한을 넘어선 양도 관측값에 남을 수 있다.

초기 실험은 13개 과제의 첫 실행 52건과 `core5` 추가 반복 40건으로 총 92건이었다. 후속 실험은 같은 13개 과제를 A~D와 두 예산에서 한 번씩 실행한 104건이다. 아래 비교표는 1배에서 첫 실행 52건, 1.5배와 2배에서 각각 52건을 사용한다. 1배의 추가 반복 40건은 별도로 해석했다.

토큰과 시간은 중단한 시도까지 포함한다. 후속 104건에서 미완료 7건은 모두 토큰 상한에 걸렸다. 시간 초과와 실행 오류는 0건이었다.

### C와 D의 완료율이 성공률로 이어진 정도

**C의 완료율은 38.5% → 76.9% → 92.3%, 성공률은 38.5% → 69.2% → 76.9%였다.** 1배에서 2배로 올리면서 완료가 7건, 채점 통과가 5건 늘었다. D의 완료율은 **38.5% → 76.9% → 100%**, 성공률은 **38.5% → 53.8% → 53.8%**였다. D는 1.5배에서 2배로 올렸을 때 3건을 더 완료했고, 두 예산 모두 채점 통과는 7건이었다.

2배에서 C와 D가 모두 통과한 과제는 7개였다. C만 통과한 과제는 `access_control-memory`, `notifications-main`, `review-expiry` 3개였다. 두 조건이 공통으로 통과한 7개에서 종료 시간 중앙값은 C 30.9초, D 22.3초였다. 이 표본에서 D의 시간상 이점과 C의 성공 건수 차이를 함께 관찰했다.

### 검토 의견이 최종 답변에 반영되지 않은 사례

`review-expiry`는 캐시 조회 함수가 만료 시각과 현재 시각이 같은 순간에도 값을 반환하는지 확인하는 과제다. 계약상 그 순간부터는 `None`을 반환해야 한다. 2배 예산의 D에서 **두 독립 검토자 모두 `cache_store.py:6`에서 `now == expires_at`일 때 오래된 값이 반환된다고 보고했다.** 그러나 두 의견을 받은 최종 에이전트는 결함이 없다는 뜻으로 `CLEAN`을 제출했다. 실행은 완료됐고, 최종 답변 채점에서 실패했다.

이 사례에서는 검토자에게 충분한 예산이 주어졌고 두 검토자가 올바른 근거까지 제공했다. 실패는 **그 근거를 최종 판단에 반영하는 단계**에서 발생했다. 독립 검토를 평가할 때 최종 성공률과 함께, 각 검토자가 어떤 문제를 찾았고 그 문제가 최종 산출물에 어떻게 반영됐는지도 기록할 이유다.

### 같은 다섯 과제를 다시 돌린 결과

| 처음부터 세 번 실행한 `core5` 과제 | A | B | C | D |
| --- | --- | --- | --- | --- |
| notifications-main | 1/3 | 1/3 | 0/3 | 0/3 |
| notifications-trap | 0/3 | 0/3 | 0/3 | 0/3 |
| billing-trap | 0/3 | 0/3 | 0/3 | 0/3 |
| notifications-memory | 1/3 | 0/3 | 0/3 | 0/3 |
| access_control-memory | 3/3 | 3/3 | 0/3 | 0/3 |

| 조건 | 세 번 실행한 과제 | 한 번 이상 성공 | 세 번 모두 성공 | 성공·실패 혼재 |
| --- | --- | --- | --- | --- |
| A | 5 | 3 | 1 | 2 |
| B | 5 | 2 | 1 | 1 |
| C | 5 | 0 | 0 | 0 |
| D | 5 | 0 | 0 | 0 |

반복에서 A의 성공·실패가 바뀐 과제는 2개, B는 1개였다. C는 코어 15회 중 13회가 토큰 상한에 걸렸고, 완료한 2회는 채점을 통과하지 못했다. D는 15회 모두 예산에 도달했다. 이처럼 고정 5개를 반복하면 특정 과제에서 점수가 흔들리는지와 예산에 막히는 현상이 반복되는지를 확인할 수 있다. 새 과제 8개를 추가하고서야 C와 D의 성공 사례도 관찰할 수 있었다.

세 번 중 한 번 이상 성공한 과제 수와 세 번 모두 성공한 과제 수를 각각 기록했다. 앞의 값은 여러 결과 중 성공한 것을 고를 수 있을 때, 뒤의 값은 재시도할 때도 일관된 결과가 필요한 경우에 참고할 수 있다. 고정된 적은 과제를 반복하는 방식은 실행기·채점·예산 중단의 회귀를 빠르게 찾는 데 쓸 수 있다. 비교 결론을 새 저장소나 다른 작업까지 넓히려면 과제 유형을 추가하고, 프롬프트를 조정할 때 보지 않은 과제로 다시 확인할 필요가 있다. [τ-bench의 반복 성공 지표](https://arxiv.org/abs/2406.12045) · [과제·벤치마크에 따른 신뢰도](https://arxiv.org/abs/2610.00651)

## 결과가 의미하는 것

**예산은 실행 기회를 결정하고, 검토 결과를 종합하는 방식은 산출물의 품질에 영향을 준다.** 1배에서는 C와 D의 낮은 성공률에 토큰 상한으로 인한 중단이 크게 작용했다. 2배에서는 대부분의 실행이 끝났고, D에서 완료 후 채점 실패가 6건 관찰됐다. 두 조건에서 관찰한 과제별 차이를 설명하려면 운영상 완료 여부, 최종 채점, 검토 의견이 전달되는 과정을 함께 봐야 한다.

운영 비용을 비교하면 2배의 A와 B도 각각 9개를 통과했고, 평균 토큰은 C·D 대비 A가 약 41%, B가 약 50%였다. 복잡한 검토가 필요한 과제에만 두 관점을 필수로 적용하거나 독립 검토를 여는 방식은 다음 실험에서 검증할 만하다. 평가할 때는 같은 과제에서 잘 끝낸 속도와, 주어진 예산에서 얼마나 자주 올바르게 끝냈는지를 함께 기록해야 한다.

## 한계점 및 향후 연구 방향

세 예산은 모델 하나와 과제 13개에서 비교했다. 과제와 조건별로 예산당 한 번씩 실행했고, 1배와 후속 두 예산은 별도 실행 기간이었다. 따라서 점수 차이가 반복 실행에서도 유지되는지는 후속 검증이 필요하다. 원본 알림 과제 일부는 소스 문자열로 채점한다. 또 작업 사본의 Git 기준 커밋을 생략해, 에이전트가 `git diff HEAD`로 변경분을 확인하기 어려웠다. 중단한 과제의 토큰과 시간은 중단 시점까지의 관측값이다. [원본 평가 범위](https://github.com/sleeplesshan/dual-brain/blob/1729cfda50c18b74029ad449aa2698a6ec558c84/benchmarks/README.md#core-suite) · [에이전트 평가에서 로그 분석의 역할](https://arxiv.org/html/2605.08545v1)

1. **최종 단계에서 검토 의견을 대조한다.** 각 발견에 파일 위치, 재현 조건, 영향을 남기고, 메인 에이전트가 반영 여부와 근거를 확인하도록 한다. 검토자의 결함 발견률과 최종 답변에 들어간 발견의 비율을 따로 비교하면 `review-expiry`와 같은 누락을 찾을 수 있다.
2. **수정과 최종 검증에 쓸 예산을 남겨 둔다.** 짧은 과제는 한 번만 검토하고, 설계 영향이 크거나 근거가 충돌할 때 독립 검토를 여는 변형을 비교할 수 있다. 파일 위치와 확인해야 할 계약을 짧게 전달하고, 검토자 입력·출력과 최종 단계에 든 토큰을 구분해 기록한다.
3. **같은 예산에서 반복하고 채점을 보강한다.** 과제군과 예산별로 반복 횟수를 맞추고, 새 저장소에서 같은 패턴이 재현되는지 확인한다. 작업 사본에는 기준 커밋을 만들고, 원본 알림 예제에는 채널 발송·사용자 설정·기존 호출 호환성에 대한 실행 검사를 추가한다.
