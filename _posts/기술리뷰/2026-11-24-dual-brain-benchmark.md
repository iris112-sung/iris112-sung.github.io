## 서론

코딩 에이전트가 한 작업에서 설계의 타당성과 구현의 정확성을 모두 검토하도록 하는 방법을 살펴보다가 Dual-Brain 저장소를 읽었다. 이 스킬은 검토를 두 역할로 나눈다. 우뇌는 설계가 문제를 해결하는지와 변경이 다른 구성 요소에 어떤 영향을 주는지 본다. 좌뇌는 실제 코드에서 입력과 출력의 계약, 경계 조건, 기존 동작을 확인한다. 메인 에이전트는 두 검토의 근거를 종합해 필요한 변경을 적용하고 최종 결과를 검증한다. 이후 작업에 필요한 결정은 프로젝트 메모리에 남길 수 있다. [Dual-Brain 한국어 README](https://github.com/sleeplesshan/dual-brain/blob/1729cfda50c18b74029ad449aa2698a6ec558c84/README.ko.md)

예를 들어 알림 발송에 Slack을 추가한다면 설계 검토에서는 기존 발송 경로를 어떻게 활용할지 살핀다. 구현 검토에서는 실제 Slack API와 기존 호출 방식, 알림을 끈 사용자의 동작을 확인한다. 두 관점이 서로 다른 문제를 본다는 점에서 이 구조에 관심이 갔다. 그렇다면 **한 에이전트가 같은 두 관점으로 검토할 때와 비교해서, 별도의 검토자에게 맡기는 방식은 같은 예산 안에서 더 많은 과제를 해결할 수 있을까?**

## 기존 평가 방식과 의문

원본 벤치마크의 `core5`는 알림 리팩터링, 오래된 API 제안 대응, 프로젝트 메모리 유지 등을 보는 과제 5개로 구성된다. 기본 설정은 초기 메모리 없는 단일 에이전트, 초기 메모리가 있는 단일 에이전트, Dual-Brain을 비교한다. `dry-run`에서 보이는 15건은 과제 5개와 설정 3개를 조합한 실행 계획이다. 초기 기록에는 단일 에이전트 3/5, Dual-Brain 4/5라는 결과가 있지만, 두 조건의 메모리 접근이 달랐고 이후 일부 채점 기준의 문제도 보고됐다. [원본 벤치마크 구성](https://github.com/sleeplesshan/dual-brain/blob/1729cfda50c18b74029ad449aa2698a6ec558c84/benchmarks/README.md#core-suite) · [초기 결과와 한계](https://github.com/sleeplesshan/dual-brain/blob/1729cfda50c18b74029ad449aa2698a6ec558c84/benchmarks/RESULTS.md) · [검증 기록](https://github.com/sleeplesshan/dual-brain/blob/1729cfda50c18b74029ad449aa2698a6ec558c84/benchmarks/VALIDATION.md)

여기서 두 가지 의문이 생겼다. 첫째, 메모리를 맞춰도 Dual-Brain 쪽에는 두 관점으로 검토하라는 지침이 추가된다. 점수가 오르더라도 역할 지침의 효과와 검토자를 분리한 효과가 섞여 있다. 둘째, 과제 5개에서는 성공 여부 하나가 점수를 20%p 바꾼다. 같은 과제를 다시 돌릴 때의 일관성과 새 과제를 줬을 때의 성능을 각각 확인할 필요가 있었다.

## 평가 방식 개선

### 검토 지침과 위임의 효과를 구분하기

*AI Agents That Matter*에서는 정확도를 비교할 때 호출 횟수를 늘리는 단순한 기준선도 고려하고, 정확도와 비용을 함께 보자고 제안한다. Kim 외의 연구는 모델과 도구, 계산 예산을 맞춰 조율 구조를 비교했다. PACE 프리프린트 역시 토큰과 호출 수처럼 동시에 달라지는 자원을 제시한다. 이를 바탕으로 메모리와 두 역할의 검토 기준을 공유하는 C와 D를 추가했다. [AI Agents That Matter](https://arxiv.org/abs/2407.01502) · [Towards a Science of Scaling Agent Systems](https://arxiv.org/html/2512.08296v3) · [PACE](https://arxiv.org/abs/2611.17610)

| 조건 | 실행 방식 |
| --- | --- |
| A | 기본 단일 에이전트. 초기 프로젝트 메모리 없음 |
| B | 단일 에이전트. C·D와 같은 초기 프로젝트 메모리와 사용 안내 제공 |
| C | B와 같은 메모리를 사용한다. 한 에이전트가 원본 스킬의 설계 검토와 코드 검토를 순서대로 수행한 뒤 구현 |
| D | C와 같은 메모리를 사용한다. 별도의 읽기 전용 Codex 컨텍스트 두 개가 병렬 검토하고, 세 번째 컨텍스트가 결과를 종합해 구현 |

C와 D에는 원본 스킬의 같은 역할 프롬프트와 변경 판단 기준을 줬다. C는 한 대화에서 앞선 검토 내용을 이어받고, D는 독립 검토자들의 요약을 구현 단계에 전달한다. 이 비교에는 별도 컨텍스트, 결과 전달, 병렬 실행의 효과가 함께 들어 있다. 원본 스킬은 간단한 과제에서 위임을 생략할 수 있다. 이번 실험에서는 위임 구조의 비용을 직접 관찰하기 위해 모든 과제의 C와 D에서 두 검토를 수행했다. D의 각 컨텍스트는 토큰을 개별 계측할 수 있도록 실험 실행기에서 시작했다. [Dual-Brain 원본 스킬](https://github.com/sleeplesshan/dual-brain/blob/1729cfda50c18b74029ad449aa2698a6ec558c84/SKILL.md)

### 같은 과제 반복과 새 과제 추가를 함께 하기

*On Randomness in Agentic Evals*는 SWE-bench Verified에서 6만 건을 실행했고, 선택한 반복에 따라 전체 성공률이 2.2~6.0%p 달라졌다고 보고했다. 반면 적은 문제로 전체를 추정하려면 과제 선정이 중요하다. `tinyBenchmarks`는 MMLU 약 1만 4천 문제에서 선별한 100개로 전체 점수를 추정했고, Princeton HAL은 SWE-bench Verified에서 뽑은 50개 과제를 경량 평가에 사용했다. 이 연구들을 참고해 `core5`는 고정한 채 세 번씩 실행하고, 버그 수정·리팩터링·코드 리뷰·메모리 갱신을 포함한 과제 8개를 더했다. 반복으로 같은 과제의 변동을 보고, 확장한 과제에서 비교 결과가 어떻게 달라지는지 확인하도록 설계했다. [On Randomness in Agentic Evals](https://arxiv.org/abs/2602.07150v3) · [How Many Tasks Are Enough](https://arxiv.org/abs/2607.12338) · [tinyBenchmarks](https://proceedings.mlr.press/v235/maia-polo24a.html) · [HAL SWE-bench Verified Mini](https://hal.cs.princeton.edu/swebench_verified_mini)

## 실험

### 실행 환경과 채점

13개 과제의 첫 실행 52건과 `core5`의 추가 반복 40건을 합해 **92건**을 실행했다. 실행 환경은 `codex-cli 0.157.1`이며, 전체 시도에서 보고된 토큰 합계는 13,681,229개였다.

모든 조건에서 `gpt-6-luna`와 추론 강도 `low`를 사용했다. 단일 세션 과제에는 130,000토큰과 120초, 다중 세션 과제에는 320,000토큰과 260초를 배정했다. 매 시도마다 별도 작업 사본에서 시작했고, 최대 네 건을 동시에 실행했다. 캐시 입력은 전체 토큰에 포함했다. 출력 안에 이미 포함된 추론 토큰도 중복 집계하지 않았다. 사용량은 모델 요청이 끝난 뒤 보고되기 때문에 관측값은 상한을 일부 넘을 수 있다. 이 경우 상한 초과로 처리했다.

예산 안에서 끝내고 별도 채점까지 통과해야 성공으로 기록했다. 신규 구현 과제는 에이전트가 남긴 파일을 복사해 숨겨진 테스트를 적용했다. 읽기 전용 리뷰 과제는 최종 판단과 결함 근거를 채점했다. 원본 과제는 기존 테스트와 소스 구조 검사를 사용했고, 메모리 파일의 문구 일치는 보조 지표로 기록했다. [최종 상태를 기준으로 한 에이전트 채점](https://www.anthropic.com/research/demystifying-evals-for-ai-agents) · [SWE-Bench Pro V2 평가 방식](https://arxiv.org/abs/2610.24206)

| 조건 | 성공 | 예산 초과 | 실행 오류 | 완료 후 채점 실패 |
| --- | --- | --- | --- | --- |
| A 기본 단일 | 7/13 (53.8%) | 0 | 0 | 6 |
| B 단일 + 메모리 | 6/13 (46.2%) | 2 | 0 | 5 |
| C 단일 + 자체 검토 | 5/13 (38.5%) | 8 | 0 | 0 |
| D 독립 검토자 2명 | 5/13 (38.5%) | 8 | 0 | 0 |

| 조건 | 전체 토큰 평균 | 캐시 입력 평균 | 출력 평균 | 완료·중단 시간 중앙값 | 95백분위 시간 |
| --- | --- | --- | --- | --- | --- |
| A | 80,514 | 66,501 | 757 | 11.4초 | 45.7초 |
| B | 95,480 | 77,982 | 981 | 13.7초 | 69.7초 |
| C | 164,648 | 142,799 | 1,469 | 29.0초 | 71.5초 |
| D | 169,115 | 136,684 | 1,579 | 22.2초 | 58.7초 |

C와 D가 모두 실행된 13개를 짝지어 비교했다. D만 성공한 과제는 0개, C만 성공한 과제는 0개였다. D−C의 차이는 +0.0%p였다. 관측한 과제별 차이가 모두 같아서 단순 재표집은 폭이 0인 구간을 만든다. 표본이 작으므로 구간을 제시하지 않고, 같은 성능이라는 결론도 보류했다. D의 평균 토큰은 C 대비 +2.7%, 시간 중앙값은 -6.8초 차이였다. 시간은 완료 또는 중단까지의 실제 경과 시간이다. 예산에 걸려 일찍 끝난 경우도 포함하므로 중앙값이 낮다고 완료까지 더 빠르다고 해석할 수는 없다. 토큰 평균은 계측이 있는 시도 기준이다.

- **예산을 쓴 위치.** C와 D의 8건 중단은 모두 토큰 상한 때문이었다. 대부분 두 검토를 마친 뒤 수정·검증을 담당하는 단계에 들어갔지만, 예산 안에서 그 단계를 끝내지 못했다. 이를 최종 코드의 오류와 구분했다.
- **리뷰 과제.** 정상 코드와 만료 경계 버그를 포함한 리뷰 2개는 네 조건 모두 맞혔다. 두 리뷰의 평균 토큰은 A 약 3.3만개, C 약 7.3만개, D 약 10.4만개였다. 이 두 사례에서는 검토를 추가한 비용만 관측됐다.
- **코드가 답변과 다를 수 있다.** `window-boundary`에서 B는 종료 시점을 제외하도록 바꿨다고 답했지만, 파일에는 종료 시점을 포함하는 기존 조건이 남았다. 반대로 C와 D는 경계 조건을 실제로 고쳐 실행 검사를 통과했다.
- **코어 표본의 영향.** 원본 5개 첫 실행에서는 C와 D가 모두 0/5였다. 신규 8개에서는 둘 다 5/8을 통과했다. 같은 설정의 성능 인상이 과제 구성에 따라 어떻게 달라지는지 보여준다.

반복에서 A의 성공·실패가 바뀐 과제는 2개, B는 1개였다. C는 코어 15회 중 13회가 토큰 상한에 걸렸고, 완료한 2회는 채점을 통과하지 못했다. D는 15회 모두 예산에 도달했다. 이처럼 고정 5개를 반복하면 특정 과제에서 점수가 흔들리는지와 예산에 막히는 현상이 반복되는지를 확인할 수 있다. 새 과제 8개를 추가하고서야 C와 D의 성공 사례도 관찰할 수 있었다.

세 번 중 한 번 이상 성공한 과제 수와 세 번 모두 성공한 과제 수를 각각 기록했다. 앞의 값은 여러 결과 중 성공한 것을 고를 수 있을 때, 뒤의 값은 재시도할 때도 일관된 결과가 필요한 경우에 참고할 수 있다. 고정된 적은 과제를 반복하는 방식은 실행기·채점·예산 중단의 회귀를 빠르게 찾는 데 쓸 수 있다. 비교 결론을 새 저장소나 다른 작업까지 넓히려면 과제 유형을 추가하고, 프롬프트를 조정할 때 보지 않은 과제로 다시 확인할 필요가 있다. ## 한계점 및 향후 연구 방향

이번에는 모델 하나와 한 종류의 예산 설정을 사용했다. 원본의 세 예제 저장소와 직접 작성한 과제도 실제 프로젝트 전반을 대표하기에는 작다. 원본 알림 과제의 일부는 소스 문자열로 채점한다. 또 각 사본에 Git을 초기화했지만 기준 커밋 생성은 생략해, 에이전트가 `git diff HEAD`로 변경분을 확인하기 어려웠다. 중단한 과제는 중단까지의 자원 사용량만 남겼다. [원본 평가 범위](https://github.com/sleeplesshan/dual-brain/blob/1729cfda50c18b74029ad449aa2698a6ec558c84/benchmarks/README.md#core-suite) · [에이전트 평가에서 로그 분석의 역할](https://arxiv.org/html/2605.08545v1)

1. **수정 예산을 먼저 확보한다.** 이번 실행의 C와 D는 각 과제에서 정해진 검토를 모두 수행했다. 간단한 과제는 한 에이전트의 짧은 자체 검토로 끝내고, 여러 구성 요소가 얽히거나 근거가 충돌할 때만 독립 검토를 여는 변형을 다음 실험에서 비교할 수 있다. 수정과 최종 테스트에 사용할 예산을 미리 남겨두면, 검토 단계가 자원을 대부분 소비하고 구현이 잘리는 문제를 직접 점검할 수 있다.
2. **검토에 반복 입력하는 맥락을 줄인다.** 첫 실행에서 각 조건 전체 토큰의 약 81~87%가 캐시 입력이었다. 원본 파일 위치, 재현 조건, 확인해야 할 계약을 짧게 전달하고, 필요한 파일을 검토자가 추가로 확인하는 방식을 비교할 수 있다. 총 토큰 외에 캐시 입력, 출력, 실제 지연을 따로 관찰해야 한다. 캐시 입력 비중은 청구액이나 실제 연산량과 동일한 지표가 아니다.
3. **기준 커밋과 실행 채점을 보강한다.** 모든 작업 사본에 기준 커밋을 만들어 에이전트 내부에서도 변경분을 확인할 수 있게 한다. 원본 알림 예제에는 기존 문자열 검사에 더해 채널 발송, 사용자 설정, 기존 호출 호환성의 실행 검사를 넣는다. 검토자가 해당 변경을 실제로 재검증했는지도 기록한다.
4. **두세 예산 구간에서 C와 D를 다시 짝지어 비교한다.** 이번 상한에서 8건이 동시에 잘렸으므로, 넉넉한 상한에서의 완료 품질과 추가 비용은 남은 질문이다. 동일한 과제에서 여러 상한의 성공률과 총토큰을 함께 기록하고, 독립 과제를 추가해 과제 유형별 결과를 확인한다. 역할 전문화의 효과까지 보고 싶다면 동일한 지시를 받은 독립 검토자 두 명을 별도 비교군으로 둘 수 있다.
